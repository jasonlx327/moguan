**版本：v0.2**  
**日期：2026 年 7 月 28 日**  
**状态：已完成源码审计、本地安装、构建与零配置运行验收**

- 上游仓库：`koala73/worldmonitor`
- 本地独立目录：`/Users/xlarge/Documents/dataworld/worldmonitor-evaluation`
- 上游版本：`2.10.0`
- 审计提交：`3645a1e29ec0d21f4cd7efec02b182c774435407`
- 主体许可证：`AGPL-3.0-only`

本次复审不再按WorldMonitor宣传的功能总数判断匹配度，而按以下问题判断：

> 在不购买WorldMonitor Pro、不依赖其私有账户体系、不使用其托管缓存，并且不假设拥有第三方数据再分发权时，墨观实际能够复用什么？

## 二、复审结论

WorldMonitor不适合作为墨观的“核心引擎”，更适合作为：

1. **观象层的开源参考实现；**
2. **地图、面板与部分数据适配器的组件来源；**
3. **数据源清单和工程架构的调研样本。**

上一版“WorldMonitor可以成为墨观主要观象底座”的判断过于乐观，现修正为：

> **墨观不应建立在WorldMonitor官方服务之上，也不应整体复制其产品。应只选择性复用可独立运行、来源明确、许可允许且确有必要的代码；墨观自行建立数据采集、事实层、事件模型和古籍推演系统。**

WorldMonitor代码开源，但界面中出现的全部数据能力并不等于全部开放。实际产品由四部分组成：

| 层次 | 实际情况 | 墨观判断 |
|---|---|---|
| 前端与可视化 | 地图、图层、面板、筛选和多站点变体在仓库中 | 可参考，按需抽取 |
| 公开数据适配器 | RSS、地震、天气、部分市场和公共机构数据可直接或自行采集 | 可选用，但逐源核验 |
| 自建运行管线 | 完整自托管需要Redis、REST代理、种子任务、AIS relay及定时运行 | 能自建，但运维成本高 |
| 官方商业能力 | 多个国家、供应链、贸易、AI与导出能力受账户、订阅或API权限约束 | 不作为墨观依赖 |

## 三、本地运行发现

### 1. 能启动，不等于完整可用

Tech变体在零配置下可以打开，地图、新闻和部分科技资讯能够显示。本地页面识别到37个面板，但首屏之后大量面板内容为空。

浏览器日志明确显示多个数据摘要缺失，包括：

- policy；
- hardware；
- finance；
- cloud；
- security；
- GitHub；
- IPO；
- funding；
- outages等。

这些分类的有限逐源回退在当前运行方式下被关闭，因此面板存在并不代表数据已经进入。

### 2. 用户截图反映的是产品边界，不是偶发故障

国家详情页中出现：

- CII不可用；
- Resilience Score持续检查访问权限；
- AI简报要求配置`GROQ_API_KEY`；
- Cost Shock Calculator要求升级Pro；
- Product Imports要求升级Pro；
- 部分国家能源数据不可用。

源码也确认，下列接口被列入Premium RPC：

- 国家韧性评分与排名；
- 国家瓶颈指数与绕行方案；
- 国家成本冲击与多行业成本冲击；
- 产品与行业依赖；
- 国家债务；
- 全球采购；
- 部分贸易流、关税与制裁压力；
- 情景模拟；
- AI事件分类、地区简报和市场影响；
- 航运路线情报等。

因此，“仓库中存在接口和页面”不能被视为“墨观获得了相应数据”。

### 3. 完整自托管不是简单启动前端

WorldMonitor自己的自托管说明要求：

- Docker或Podman；
- Redis及REST代理；
- Relay共享密钥、Redis密码和令牌；
- 执行种子任务写入数据；
- 按数据类型配置可选第三方密钥；
- 为持续更新设置定时任务。

与墨观相关的可选来源还可能需要：

- GROQ、OpenRouter或本地模型；
- FRED、EIA、Finnhub；
- ACLED；
- NASA FIRMS；
- AISStream；
- AviationStack；
- Cloudflare Radar等。

这意味着WorldMonitor是一套需要运营的数据产品工程，而不是一份天然完整的开放数据包。

## 四、与墨观的匹配度

| 模块 | 匹配度 | 结论 |
|---|---:|---|
| 2D/3D地图与图层框架 | 高 | 可作为技术参考，避免照搬界面 |
| RSS与公开新闻适配 | 中高 | 可复用方法和部分适配器，必须回到原文 |
| 公共灾害与天气数据 | 中高 | 与“观象”有关，可独立接入权威源 |
| 半导体与AI产业新闻 | 中 | 适合发现线索，不足以建立政策事实链 |
| 航空、船舶与基础设施 | 中低 | 依赖relay、密钥或特定提供商，按专题决定 |
| 国家风险与韧性评分 | 低 | 有商业与方法体系绑定，不采用其结论 |
| 贸易、产品进口和成本冲击 | 低 | 多项受Pro接口约束，墨观应另建公开数据方案 |
| AI简报与事件分类 | 低 | 模型与服务可替换，且不符合墨观古籍推演方法 |
| 事势星云 | 低 | WorldMonitor只有信号聚合，不具备墨观所需的可审计关系层 |
| 古籍知识库与通变 | 无 | 必须由墨观独立建设 |
| 候验账本 | 无 | 必须由墨观独立建设 |

综合判断：

- **作为完整核心引擎：不匹配；**
- **作为观象前端参考：较匹配；**
- **作为数据源目录与适配器仓库：部分匹配；**
- **作为墨观推演系统：不匹配。**

## 五、对首个事件的真实价值

新版墨观首个完整验证事件为：

> **全球半导体出口管制与AI芯片供应链重组**

WorldMonitor可以贡献：

- 科技、半导体和硬件新闻候选；
- 美国、欧洲、中国相关报道线索；
- 相关企业与市场同期变化；
- 地图、时间和跨区域展示框架。

WorldMonitor不能替墨观完成：

- 美国BIS与Federal Register规则版本解析；
- 欧盟及荷兰出口管制事实；
- 中国商务部、工信部等官方回应；
- 产品、技术、主体、地域、许可和生效日期的结构化；
- 中美欧政策之间的可审计关系；
- 古籍依据、通变推演和候验记录。

所以即使采用它，半导体事件的主体工程仍然属于墨观。

## 六、建议保留与放弃

### 建议保留研究

1. `deck.gl + MapLibre GL`平面地图实现；
2. `globe.gl + Three.js`三维地球实现，暂不直接采用其视觉；
3. 面板注册、图层开关和多源时间状态设计；
4. RSS源组织、去重与来源分级思路；
5. 对确属公开数据的少量适配器；
6. 服务健康、缓存新鲜度和降级状态的工程做法。

### 不建议接入

1. WorldMonitor账户、订阅和Pro权限体系；
2. 官方托管API作为墨观长期依赖；
3. CII、Resilience Score等现成评分；
4. AI简报、Deduction、Market Implications等现成结论；
5. Cost Shock、Product Imports等商业接口；
6. 其品牌、视觉布局和“中央情报面板”式首页；
7. 为了保留大量无关图层而整体维护上游代码。

## 七、墨观应采用的技术关系

建议把WorldMonitor从“底座”降级为“上游参考仓库”，形成以下关系：

```text
公开权威来源 ─┐
公开新闻源   ─┼─→ 墨观自有采集与来源登记 ─→ 纪事 ─→ 察势 ─→ 稽古 ─→ 通变 ─→ 候验
选用的开源适配器 ─┘                         │
                                             └─→ 墨观自有地图与事势星云

WorldMonitor：
只提供被审计通过的代码参考、少量适配器和可视化经验，
不提供墨观的事实权威、推演结论或产品运行依赖。
```

## 八、采用条件

任何WorldMonitor代码进入墨观前，必须逐项回答：

1. 这段代码是否可以脱离WorldMonitor官方账户与API运行？
2. 上游数据是否公开、稳定并允许我们的使用方式？
3. 是否可以标明原始来源、采集时间和不可用状态？
4. 是否比墨观直接接权威来源更省成本？
5. 是否会把AGPL义务扩展到我们未准备公开的部分？
6. 是否真正服务于六步法，而不是增加无关功能？

只有六项均通过，才进入墨观代码库。

## 九、最终决定

WorldMonitor值得继续研究，但不再把它当成墨观的核心引擎。

下一步不应继续安装更多WorldMonitor能力，也不应购买Pro来填满页面，而应：

1. 为半导体事件建立墨观自己的三方官方来源适配器；
2. 定义最小事件事实模型；
3. 只从WorldMonitor抽取一个地图实现和一套RSS处理思路做技术对照；
4. 用同一批真实数据比较“自主实现”与“选择性复用”的开发成本；
5. 再决定是否引入任何上游代码。

这条路线保留了WorldMonitor的工程价值，也避免墨观变成一个依赖他人商业数据层的换皮Dashboard。
